## 1. 목적과 비목적

### 목적
- 사람이 미리 써두지 않은 **임의의 다자 대화**에 대해, 교착 감지 → 트리거 → 투표/장소 카드 → 합의 → 확정 흐름이 **깨지지 않는지**를 검증한다.
- 전시 전 **하루 안에** 돌려 GO/NO-GO 자신감을 확보한다.

### 비목적 (이번 스윗에서 다루지 않음)
- 단일 입력 자연어 fuzzing (은어/오타/이모지 단건) — 기존 K2 러너 영역.
- 신규 사용자 온보딩 흐름 — 기존 K3.3 러너 영역.
- 프론트엔드 렌더링 검증 — API/WS 레벨만 본다 (브라우저 미구동).
- 재사용 가능한 CI 하니스화 — 이번엔 전시 전 스윗. 나중에 승격 가능하도록 구조만 깔끔히.

|---|---|---|
| **견고성 (넓게)** | LLM 시뮬레이터가 만든 임의 다자 대화 전부 | 하드 불변조건 (§5) — 크래시·행·유실·SLA 위반 없음 |
| **정확성 (핵심만)** | S1~S10 다자 확장 결정적 시나리오 | 기대 카드 타입·내용 정확 assert (§7) |
| **소프트 품질** | 견고성 대화의 전사 샘플 | LLM 심판관 (§8) — "응답이 맥락에 말이 되는가" |

## 3. 전체 구조 — 역할 분담

두 주체로 나눈다.

- **스크립트 (`.gstack-robustness-sweep.py`, Python)** — 판단이 필요 없는 기계적 검증 전부:
  방 생성·다자 대화 구동·하드 불변조건 체크·동시성 부하·전사 저장·지연 측정·정확성 assert.
- **Claude (심판관, 스크립트 밖)** — 스크립트가 남긴 전사를 읽고 소프트 품질 채점 + GO/NO-GO 리포트 합성.

**심판관을 스크립트 밖 Claude로 분리하는 이유**: 사용자 시뮬레이터와 시스템(파이프라인)이 둘 다 Gemini라, 판정자까지 Gemini면 실패 모드가 겹쳐 "둘 다 같은 헛소리를 정상으로 통과"시킬 수 있다. 판정자만은 다른 모델(Claude)이어야 한다. 추가 API 배선도 불필요.

```
.gstack-robustness-sweep.py
  ├─ Setup        REST 방 생성·초대·입장 (멀티 유저 JWT)
  ├─ Drive        페르소나 발화 생성(Gemini→fallback) → /ws/agent 주입 → 카드 관찰
  ├─ Invariants   매 턴/카드 인라인 체크 (§5)
  ├─ Concurrency  M개 방 asyncio 동시 + 동시 액션 주입 (§6)
  ├─ Correctness  S1~S10 다자 확장 결정적 assert (§7)
  └─ Output       전사 JSON/MD + 지연/동시성/정확성 요약 → 출력 디렉터리
                          │
                          ▼
       Claude 심판관: 전사 읽기 → 소프트 채점 → GO/NO-GO 리포트
```

## 4. 대화 생성 — 페르소나 + LLM 시뮬레이터

각 멤버의 다음 발화를 페르소나 프롬프트 시드 + 대화 맥락으로 Gemini(기존 `openai_client`/Gemini client 재사용)에 생성시킨다. **rate limit 시 페르소나별 템플릿 발화 뱅크로 fallback** (CLAUDE.md 룰: Gemini rate limit 시 패턴 fallback으로 기본 동작 보장).

### 페르소나 7종 (방마다 3~5명 랜덤 조합)
1. **주도형 호스트** — 모임을 적극 추진, "다음주에 모이자" 류 직접 요청
2. **잠수형** — 늦게 한 마디, 대부분 무응답
3. **까다로운 거절러** — 여러 날 연속 거절("월요일 안돼", "화요일도 별로")
4. **모호한 시간러** — "다다음주 언제쯤", "조만간" 같은 비확정 표현
5. **게스트** — 캘린더 연동 없음, 가용성 데이터 부재
6. **단답·이모지형** — "ㅇㅋ", "👍", "아무때나"
7. **주제 이탈러** — 딴소리·잡담을 흐름에 섞음

각 페르소나는 숨은 목표(hidden goal)를 가지며, 라운드로빈으로 발화. "사람이 안 쓸 대화"까지 뒤집어 견고성을 넓힌다.

### 트리거 사유 커버리지
5개 트리거 사유를 자연스럽게 유발하도록 대화를 구성:
`stalemate_judged` / `direct_request` / `all_members_selected` / `conclusion_detected` / `preference_toggle`

## 5. 하드 불변조건 (스크립트, 인라인, 매 턴/카드)

이 중 **하나라도** 위반하면 그 대화는 FAIL로 플래그.

1. **무예외**: 백엔드 5xx·WS 에러 프레임·파이프라인 예외 0건.
2. **SLA**: 트리거 → 첫 카드 지연을 매번 기록, **p95 < 8s** (K1 SLA). 개별 트리거 행(hang)·무한대기 0.
3. **무유실**: 모든 트리거는 반드시 유효한 응답(카드 또는 assistant 메시지)을 산출. 침묵 드롭 0.
4. **payload 정합성**:
   - `vote_card`: vote_options 비어있지 않음, 날짜 범위 유효
   - `maedeup_card`: confirmed_date + confirmed_place 둘 다 존재
   - `place_recommendation`: 검색 결과 비어있지 않음
5. **상태 정합성**:
   - 확정(finalization) 후 다른 화면의 추천/투표 카드 소거 (회귀: commit 566b98e)
   - 동일 카드 중복 발급 없음
   - 투표수 단조 증가 (감소·음수 없음)
6. **WS 브로드캐스트**: 방에 연결된 전 멤버가 카드 이벤트 수신. 누락 0 (K3.2).

---

## 6. 동시성·병렬 부하 (B 요소)

별도 Workflow가 아니라 **한 스크립트 내 asyncio**로 녹인다.

- **병렬 부하**: M개 방을 동시 구동 → 진짜 병렬 백엔드 부하. 부하 중에도 §5 불변조건이 버티는지 확인.
- **동시 액션 주입** (지정 방): 
  - 전원 동시 투표 → race condition (K3.1)
  - 2명 동시 트리거 → 카드 중복·브로드캐스트 누락 (K3.2)

## 7. 정확성 레이어 (결정적 서브셋)

S1~S10(`spec-time-coordination.md`)을 **다자판 스크립트 대화**로 확장. 발화가 고정되어 있어 기대 출력이 결정적이므로, 카드 타입·핵심 내용을 정확히 assert.

| 시나리오 | 입력(요지) | 기대 |
|---|---|---|
| S1 기본 시간 투표 | "다음주에 모이자" | vote_card 3~5 슬롯 |
| S2 거절 누적 | "월요일 안돼" | vote_card에서 월요일 제외 |
| S4 다음주 확장 | "이번주"(전원 불가) | vote_card + "확장했어요" 내레이션 |
| S6 TimeBar 합의 | 전원 TimeBar 선택 | 공통 슬롯 기반 vote_card |
| S8 다수결 fallback | 전원 공통 가용 없음 | vote_card + "전원 가능 없음" 내레이션 (F1) |
| S9 시간 단독 partial | "다음주 화요일 6시" | maedeup_card (time_only partial) |
| S10 결론 자동감지 | 채팅 합의 | maedeup_card 직접 |

(S3/S5/S7은 시간 여유에 따라 선택 포함. 최소 위 7개.)

## 8. LLM 심판관 (Claude, 스크립트 밖)

스크립트 종료 후, Claude가 전사를 읽고 채점:
- **샘플링**: 견고성 대화 전사 중 (a) 불변조건 통과분 표본 + (b) 플래그된 실패 전부.
- **채점 기준**: "AI 응답이 그 대화 맥락에 말이 되는가? 카드가 적절한가? 동문서답·뜬금없음·페르소나 무시 없나?"
- **출력**: 소프트 실패 플래그 + 근거(전사 인용).

토큰 바운드를 위해 전수가 아닌 표본 채점. 표본 규모는 스윗 실행 시 결정.

## 9. 산출물 & 리포트

스윗 출력 디렉터리 (예: `docs/handoff/robustness-sweep-2026-06-03/`):
- **전사**: 방별 JSON/MD (발화·트리거·카드·타이밍·불변조건 결과)
- **지연**: 트리거→카드 퍼센타일 (p50/p95, K1)
- **동시성**: race/브로드캐스트 결과 (K3)
- **정확성**: S-시나리오 pass/fail 표
- **심판관**: 소프트 실패 플래그 (Claude 합성)
- **GO/NO-GO 요약**: 전시 의사결정용 한 장

## 10. 호출 방식 (파라미터화)

정식화된 명령 예:
> "전시 견고성 스윗 돌려줘 — 방 30개, 페르소나 랜덤, 동시 8개 부하, 불변조건 전부 + 핵심 S-시나리오 정확성, 끝나면 전사 심판하고 GO/NO-GO 리포트."

파라미터:
- `--rooms N` 총 방 수
- `--concurrency M` 동시 구동 방 수
- `--personas random|fixed` 페르소나 조합 방식
- `--scenarios core|all` 정확성 서브셋 범위
- `--time-box <분>` 시간 박스 (초과 시 진행분까지 리포트)

규모·시간 박스만 바꿔 부르면 동일 스크립트로 재실행.

## 11. 사전 조건 / 의존성

- `docker compose up -d` 로 백엔드·프론트·DB·Redis 기동.
- 멀티 유저 JWT 확보 (기존 `.gstack-demo-token` 패턴 확장 — 다자 방엔 N개 토큰 필요).
- `GEMINI_API_KEY` (시뮬레이터 발화 생성용; rate limit 시 템플릿 fallback).
- 기존 러너 인프라 재사용: K3 concurrency 러너의 다자 방·WS 다중 리스너 패턴.

## 12. 리스크 / 한계

- **시뮬레이터·시스템 모델 공유**: 둘 다 Gemini → 심판관을 Claude로 분리해 완화 (§3).
- **Gemini rate limit**: 다자×다방이면 호출 폭증 → 템플릿 fallback + 호출 백오프 필수.
- **비결정성**: 견고성 레이어는 매 실행 다른 대화 → 재현은 전사 저장으로 보완(실패 전사로 회귀 케이스 추출 가능).
- **프론트 미검증**: API/WS만 봄. 렌더링 회귀(예: 모바일 깨짐)는 별도 — 전시는 데스크탑이라 리스크 제한적.
- **부하 규모**: asyncio 단일 프로세스라 진짜 대규모 동시성엔 한계. 전시 관람객 수준(소~중 동시)엔 충분.
